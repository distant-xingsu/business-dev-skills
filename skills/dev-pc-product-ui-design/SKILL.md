# PC 产品界面设计

目标是让业务呈现、空间利用和代码职责一起改善。先识别当前项目已有的完成页面和公共能力，再决定布局与视觉；技能不依赖任何个人路径或其他技能。

## 职责与配合

本技能负责界面如何组织、呈现和表达。接口契约、请求竞态与保存回读属于业务接口联调；菜单到服务端的数据范围和状态规则属于业务权限与流程；画布、撤销重做和编辑快照属于编辑器状态与操作。只有任务实际跨越这些边界时才结合相应指导，不默认加载整套技能；已有交互与状态边界仍须在界面改动中保持。

## 优先采用的设计方法

以用户长期开发设计的 CRM 桌面端成熟页面为主要参考，而不是泛指某类 SaaS 模板。参考其分组、间距、表单、搜索表格、弹层与反馈方式；优先当前项目已认可的基准，未成型页面再选择 CRM 的同类能力。开发阶段的多项目智能体系统可借鉴这些视觉与操作模式，但对话、证据、草稿和执行结果仍按自身任务组织，不能强套客户列表。

先判断目标是桌面客户端还是浏览器应用，以及页面所处开发阶段；复用设计理由，在目标项目的组件、主题和布局中实现。CRM 的 Electron/IPC、业务权限、固定尺寸及专用依赖不随样式迁移。参考源码或截图不可用时说明依据不足，不虚构已对照。以下方法只采用本次需要的部分。

| 希望改善的体验 | 优先采用的方法 | 适用范围与详细指导 |
| --- | --- | --- |
| 更多业务内容可见，常用操作易找到 | 查询、操作、记录、分页分区；公共布局统一空间分配 | 记录型页面，见布局与页面模式 |
| 同类页面操作习惯一致 | 复用搜索、表格分页、空状态的完整契约 | 列表新建或统一改造，见 Vue 组件契约 |
| 信息多但仍易扫读 | 识别信息与关键状态优先，普通只读信息使用文字，动作有主次 | 列表和详情，见视觉决策 |
| 连续查阅和处理记录不丢上下文 | 保留已有返回位置与查询条件，局部刷新、局部重试 | 列表到详情或编辑流程，见布局与页面模式 |
| 增加功能时职责仍清楚 | 页面编排，独立业务弹层管理草稿，可复用生命周期放 composable | Vue 页面，见 Vue 组件契约 |
| 保存结果可理解、后续能继续操作 | 明确草稿与后台保存范围，按真实请求结果反馈 | 填报、表单和编辑器，见 Vue 组件契约 |

## 工作方式

1. 先明确目标页面、状态和完成条件，按任务读取适用项目规则与相关实现。局部文案/样式只查目标及直接依赖；新建或重排页面再确认框架、运行载体、路由、布局与状态组织，参考一个同类完成页面。修改公共组件前核对实现和直接调用方，不凭名字猜接口，不因续聊重复扫描。
2. 优化任务先检查原页面及实际状态，记录可观察问题和影响：例如搜索占据半屏、分页被挤走、详情信息难找、编辑草稿与表格记录共用对象。区分代码证据、截图证据和待验证推测。
3. 按改动规模说明设计决定：局部修正一句话交代问题与修改点；新建或明显重排布局时说明主任务、页面骨架、区域宽高/滚动、操作优先级、复用组件及状态归属，并用真实字段名称画线框。不要只写“简洁、高级、现代”。
4. 已获实施授权则继续。用户要求先审方案时停在方案；新增可选功能或改变业务规则时集中询问真正影响本次任务的部分。已确认事项不重复问。
5. 按已确认问题修改；若高度与滚动妨碍本次布局，先解决空间分配，再调整相关分区、组件职责和视觉细节。纯文案或样式任务不自动扩成结构重构，不能借优化改变字段、默认筛选、排序、权限、数据范围或操作语义。
6. 按修改批次选择最小有效验证，复用仍覆盖当前实现的证据。界面变化缺少适用证据时，在真实载体核验受影响布局和交互，通常先选一个代表性桌面视口。说明具体改善和未验项；类型检查、构建和 Markdown 校验不能代替视觉验收。仅修改技能或项目文档时核对内容、差异和链接，不启动业务应用。

## 按任务读取

- 新建页面或重排布局：读 [布局与页面模式](references/layout-and-components.md)。
- 按设计稿实现、改善功能入口或迁移已有页面：读 [设计对照、入口与迁移](references/design-entry-migration.md)，只展开当前场景。
- 视觉不统一、密度失控或缺乏设计方向：读 [视觉决策](references/visual-decisions.md)。
- 常用按钮优先配置语义明确的 Carbon 图标，图标与主题、操作颜色保持一致；具体选择与复用边界见视觉决策。
- 搜索、表格、详情按需读取、弹层、保存与状态边界：读 [Vue 组件契约](references/vue-component-contracts.md)。
- 按钮、弹层标题、消息提示、校验与空态用词统一：读 [界面文案与操作反馈](references/ui-copywriting.md)。
- 表单对齐、输入宽度、文字截断、滚动或拖拽反馈：读 [内容与操作布局](references/content-and-interaction.md)。
- 实现完成或审查页面：读 [验收与反例](references/desktop-ui-checklist.md)。

大型页面同时涉及多个问题时读取对应几份文档；不一次加载无关内容。

## 必须保持的判断边界

- PC 业务优先，不要求移动端布局。依据可用窗口宽高伸缩，支持超宽屏，不以 1920/2560 为最大宽度；正文可限阅读宽度，业务工作区保持伸展。
- “紧凑”指页面与区块的内外边距、区域间距和留白收敛，优先调整 padding、margin、gap 及消除叠加间距；不等于使用 size="small"，不自动缩小控件、字号或表格行高。控件尺寸沿用项目约定，只有明确的尺寸需求才调整。同层间距统一，不强制 24px，不放重复大标题、装饰性指标和无作用空区。
- 先识别列表、详情、填报、看板或编辑器。CRM 式布局主要用于记录查询与处理；日历、画布和高频编辑工作区保留其业务导航、操作方式和编辑状态，不强套搜索加表格骨架。
- 外壳、Tabs 和布局切换沿用项目；页面各有可定位的入口，局部组件按业务归属组织。具体空间与拆分规则分别见布局、组件契约，不强制迁移目录或生成整套组件。
- 沿用现有 UI 库和图标封装；Element 专用示例只适用于 Element 项目，不自动安装依赖、下载图标或替换组件库。
- i18n、主题/暗色切换、WebSocket、缓存持久化、Tabs、布局切换、导出等按业务需要并在新增前确认。已有能力直接遵循；统一语义样式变量并不意味着新增主题切换。
- 新项目未确定 Vue/UI 时先确认；现有项目先读事实，不能强行迁移到 Vue/Element。
- 接口未接、请求失败、无数据分别表达，不伪造成功或业务记录。演示数据须明确允许、隔离标识。
- 不把参考项目的业务规则、固定像素、权限码、IPC、某种语言或专用依赖提升为通用要求。
