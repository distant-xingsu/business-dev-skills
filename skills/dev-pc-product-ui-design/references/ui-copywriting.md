# 界面文案与操作反馈

用于统一按钮、弹层标题、表单提示、状态和消息反馈。先识别控件的真实行为，再选择词语；同一动作在同一项目使用同一称呼。当前明确要求优先于历史页面，历史混用只作为待整理的现状，不作为规范依据。

## 按钮与位置

| 位置与行为 | 统一用词 | 使用说明 |
| --- | --- | --- |
| 弹窗/抽屉底部，仅退出当前弹层 | 取消 | 编辑、选择、查看类弹层的普通退出入口统一使用；不混用关闭、返回、退出 |
| 独立详情页回到来源页面 | 返回 | 属于页面导航，保留原查询、页码及返回约定 |
| 新增/编辑表单写入数据，未发起审批等流程 | 保存 | 新增表单也可使用保存；不因 handler 名为 submit 就写提交 |
| 提交审核、申请或正式业务流程 | 提交；必要时为提交审核/提交申请 | 与仅保存资料区分；若明确同时保存并提交，可用保存并提交 |
| 选择对象、范围或配置后回填上层，尚未保存后台 | 确认；需要说明对象时为确认选择 | 不用保存暗示已经持久化；确认/确定不混用，默认确认 |
| 删除、导入、分配等明确业务动作 | 删除、确认导入、确认分配等 | 按动作命名，避免全用确认让用户猜结果 |
| 列表打开新增表单 | 新增；必要时为新增客户等 | 同模块同类入口保持一致，不轮换添加、新建、创建 |
| 筛选提交与恢复默认条件 | 沿用项目统一的搜索或查询；重置 | 同项目不随页面混用搜索/查询；重置不同于清空，不改变原默认条件 |
| 保存/提交进行中 | 保存中…、提交中… | 若项目只用 loading 图标并保持原文，沿用即可；不提前显示成功 |

弹层底部通常左侧为取消，右侧为本次主动作；附加动作按现有布局放置。按钮名称跟随真实动作，不单凭左/右位置或 primary 样式决定。改文案不顺带改关闭行为、路由、权限或业务状态。

这里的“取消”表示离开当前弹层，不撤回已保存数据、不取消已执行任务。真正的业务动作应写全对象，例如取消订单、取消任务；实际关闭业务对象时可用关闭工单。浏览器/系统窗口的关闭、技术事件 close 和字段名不做文案替换。

## 确认框与未保存退出

确认框标题写清动作，正文说明对象与已确认的后果；主按钮表达执行动作，次按钮一般为取消。不要只写“提示”“是否确认操作”，也不要为每次普通保存新增二次确认。

| 场景 | 标题与正文示例 | 按钮 |
| --- | --- | --- |
| 删除记录 | 删除客户；确认删除客户“某公司”吗？ | 取消 / 删除 |
| 取消实际业务 | 取消订单；确认取消订单“订单编号”吗？ | 取消 / 确认取消 |
| 放弃未保存修改 | 放弃修改；当前修改尚未保存，是否放弃本次修改？ | 继续编辑 / 放弃修改 |

“继续编辑 / 放弃修改”是明确的决策按钮，不套用普通退出按钮规则，避免出现两个含义不明的取消。只有服务端契约确认不可恢复时，正文才加“删除后无法恢复”；不能把解绑、作废、撤回、取消和删除互换。

## 成功提示：动作对应结果

短提示默认不加句号或感叹号，不混用“成功！”“成功啦”“操作完成”等近义表达。上下文清楚时用“动作 + 成功”；跨对象或容易混淆时加业务对象。

| 已确认结果 | 推荐提示 | 不应使用 |
| --- | --- | --- |
| 表单已保存后台 | 保存成功；必要时为客户资料保存成功 | 提交成功、操作成功 |
| 已发起申请或审核 | 提交成功；必要时为审核申请提交成功 | 保存成功、审核通过 |
| 删除完成 | 删除成功 | 操作成功 |
| 业务订单取消完成 | 订单取消成功 | 退出弹框时提示取消成功 |
| 分配、撤回、作废完成 | 分配成功、撤回成功、作废成功 | 用删除成功替代作废成功 |
| 修改仅进入本地草稿 | 已加入草稿、草稿已更新 | 保存成功、已同步后台 |
| 异步任务仅被接收 | 导出任务已提交、导入任务已提交 | 导出成功、导入成功 |
| 普通退出、查看、切换页签、选择后回填 | 通常不弹成功提示 | 取消成功、关闭成功、查询成功 |

业务动作可识别时不用笼统的“操作成功”。只有无法提供动作名称的既有通用反馈入口才保留该兜底；业务调用优先传入具体动作。同一用例的按钮、确认框、进行态和结果应能对应，例如“保存 → 保存中… → 保存成功”，而不是“确认 → 提交中 → 操作成功”。

成功以当前操作的真实结果为准。保存已成功但列表刷新失败，应表达“保存成功，列表刷新失败，请刷新列表”，不能报保存失败诱导重复提交。打印对话框已打开不等于已打印，下载已开始不等于文件已保存。

## 失败、校验与批量反馈

- 字段错误靠近字段：请输入客户名称、请选择所属部门、开始日期不能晚于结束日期；占位提示不替代表单标签，不只写输入有误。
- 已明确失败且可安全重试时使用“保存失败，请重试”“加载失败，请重试”。有可操作的具体原因时优先表达，例如“该记录已被修改，请刷新后重试”；不直接暴露 SQL、堆栈、内部路径等技术报错。
- 请求超时、回包不完整等结果未知时，表达“保存结果未确认，请先刷新核对”，沿用项目的核对或幂等机制；不能统一改成“保存失败，请重试”。
- 用户取消确认框或文件选择不属于失败，不弹错误或成功消息；异常分支区分主动取消与真实请求错误。
- 批量结果沿用既有公共封装，按真实返回显示“导入：成功 8 条，失败 2 条”；部分失败用警告并提供已有失败详情入口，全失败用错误，全成功才用成功。跳过数按接口单独展示，不推测不存在的计数。
- 同一次结果只由一个已有反馈层提示；请求层与页面不重复 toast，不在短暂 toast 中放必须长期阅读的失败明细。

## 标题、空态和说明文字

- 弹层标题描述任务或对象：新增客户、编辑客户、客户详情、导入联系人；与入口动作一致，不都叫操作或信息。
- 空列表用“暂无客户记录”，查询无匹配结果用“未找到符合条件的记录”；请求失败用加载失败，接口未接表达能力未接通，不能都伪装成暂无数据。
- 字段名、状态名和对象名沿用业务词汇；同一对象不交替称客户/企业/单位，除非业务确有区别。缺失值、未填写和有效的 0 分开处理。
- 简短按钮和结果短语不加末尾标点；完整说明句使用中文标点。数量带单位、限制写清条件，不用“若干”“可能不支持”等模糊文案代替已知契约。

## 提示的显示时机与空间

普通解释不默认常驻 Alert。先判断用户此刻是否需要据此采取行动，再选择呈现：字段格式靠近字段或按需帮助，低频解释放 tooltip/帮助入口，一次操作结果用既有短消息，局部失败在所属区域提供重试；影响当前任务的持续阻塞或风险才保留明确的区域提示。

状态解除后撤掉对应提示，不为“页面显得完整”常驻开发说明、接口实现细节或重复操作指南。开发阶段未接通的能力仍须真实表达，可在对应空态或操作处说明；不能为了少提示而伪装可用。必要业务警告不因紧凑而隐藏，也不擅自增加关闭或永久记住功能。

Alert 与上方工具栏、下方表单/表格之间使用项目已有的区域间距，由一个容器统一负责；同层提示间距一致。出现时不紧贴，隐藏时不留下空占位，不由 Alert 和页面各叠一次 margin。核对长文换行、关闭按钮和错误提示共存时的布局。

用户可见名称按项目语言与业务术语表达；接口方法名、code 和调试标识不直接充当标题。技术标识仅在定位、复制或调试确有用途时保留，不把某项目“只要中文”推广为删除所有技术字段。

## 整理与验收方式

先按“页面/弹层 + 当前状态 + 点击后的实际行为”登记本次用词，选定同类场景的一套词，再修改受影响文案。可搜索近义词定位，但不能全库机械替换关闭、取消、确认或成功字符串，也不为文案统一改 API 名、枚举、日志或服务端返回契约。

复用现有消息封装与既有 i18n；没有 i18n 时不为本任务新增。确有跨页面重复的文案映射才放入现有公共位置，不为几个按钮另建文案框架。

核验受影响的标题、按钮、loading 和结果是否一致，按钮变长是否挤压布局；涉及本次场景时验证普通取消不报成功、业务取消不误作关闭、部分失败不报全成功。不因纯文案修改追加全量类型检查或构建。只整理本规范时检查文本、引用和差异即可。
