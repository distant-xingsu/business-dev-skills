# 设计对照、入口与迁移

## 按设计稿实现

设计稿、HTML 原型、截图和标注同时包含视觉与交互信息。先结合用户最新要求，核对本次入口、动作顺序、编辑位置、确认后的结果及明确排除项；已有证据足够时直接实施，不重复要求确认。

- 将参考映射到目标页面、区块、控件及状态。截图没有展示的流程结合现有实现判断，不凭空补功能；用户划掉的部分不实现。
- 保留已确认的交互结构。选择器、行内编辑、普通表单、只读详情承担不同任务，不能为了套用现有组件而互换。
- 分开核对“选择对象”和“保存业务记录”。选择完成不等于后台保存成功，弹层确认后的落点与下一步操作应明确。
- 局部视觉反馈只修相关区域；发现参考与真实契约冲突时，说明冲突并只澄清影响业务的部分。

例如参考要求“打开设备与属性分组选择器 → 选择属性 → 表格行内补充字段 → 保存”，实现时应沿这条链核对。不能自行改成一个新增表单弹窗，也不把这个案例变成所有新增操作的固定模式。

## 功能入口与查找效率

仅在任务涉及入口梳理时，基于当前路由、菜单、实际页面及使用场景判断；旧菜单清单不能直接作为缺入口的证据。

| 场景 | 优先考虑 | 判断代价 |
| --- | --- | --- |
| 高频、跨记录使用、具有独立任务与访问地址 | 独立页面或已有菜单入口 | 是否与现有总览重复、是否增加导航负担 |
| 依赖当前记录、选择集合或当前流程状态 | 页内动作、行操作或上下文入口 | 离开上下文是否容易操作错对象 |
| 常用功能已有入口但查找路径较长 | 现有快捷入口，或任务已授权的功能检索 | 名称和别名维护、权限过滤及失效入口处理 |
| 低频辅助操作 | 项目已有的次级操作区 | 不将关键主动作藏入“更多” |

区分“找功能”与“查业务记录”。功能结果应表达名称和所在层级，业务结果表达对象及必要上下文；两者复用真实授权入口，不以搜索结果存在推定可访问。

将功能从弹层提升为页面时，先判断是否真正需要独立地址和跨对象使用，复用原有业务能力，保留必要来源、返回和筛选上下文。只提出建议的任务不实施菜单新增、权限调整或全局重排。

## 按需提供迁移清单

用户要求跨系统复用或迁移页面时，从实际 import、组件注册和运行依赖提炼最小闭包，不只列主页面，也不默认搬走整个业务模块。

清单区分：

- 必需文件：入口、私有组件、直接使用的 composable、类型及资源。
- 可替换公共依赖：布局、表格、图标、主题变量与公共样式；说明依赖的公开契约。
- 目标系统适配：框架和 UI 库版本、请求封装、鉴权与响应结构、路由参数、权限入口、事件和返回路径。
- 条件依赖：仅当保留关联功能时才携带的其他页面或模块；明确移除入口时相应的事件处理。

用户只问迁移哪些文件时给清单，不直接复制或重构。实际迁移按授权检查目标系统，保留接口与业务语义；类型耦合优先使用模块公开接口，不访问另一页面的私有实现。按受影响链验证，不为了迁移清单运行全项目构建。
