# 视觉决策

## 从已完成页面建立基准

先观察已认可页面和主题变量，列出其标题、正文、标签、控件高度、搜索宽度、行密度、背景和边框层级。区分项目已有的视觉语言与局部实现缺陷；不因为“优化”就更换整套颜色、字体或图标。

视觉改造需要回答：用户先看哪组信息、哪里开始操作、哪些记录可比较、哪个状态要引起注意。每项调整应能解释如何帮助这些任务。

## 紧凑布局的含义

紧凑优先指内外边距：收敛页面边缘留白、区块 padding、区块之间的 margin/gap，消除布局与业务容器叠加的间距。保留必要分组与阅读空间，不把所有间距清零。

“紧凑主题/紧凑布局”本身不构成设置 size="small" 的依据，也不要求缩小按钮、输入框、选择器、字号或表格行高。沿用项目当前控件尺寸；只有用户明确要求或已确认的独立尺寸需求才调整，不通过全局 size 配置把整个界面缩小。

## 无既定规范时的起始尺度

以下是试排区间，不是项目硬性标准。实际组件测量优先，尤其要核对项目是否已有 rem/缩放转换。

| 元素 | 起始参考 | 调整依据 |
| --- | --- | --- |
| 业务正文 | 14px | 当前字体、阅读距离、数据密度 |
| 辅助信息 | 12–13px | 不承载唯一关键业务信息，确保对比度 |
| 区块标题 | 14–16px、中等字重 | 区分信息组，不抢主内容 |
| 必要页面标题 | 18–20px | 外壳已提供标题则不重复 |
| 常规控件 | 项目当前或组件库默认尺寸 | 同排按钮/输入/选择外框实测对齐，不因紧凑改为 small |
| 表格行 | 项目当前或组件库默认行高 | 根据内容与编辑需求保持可读性，不为紧凑强行压低 |
| 组内间距 | 约 4–8px | 图标文字、小型操作组合 |
| 区域/内容留白 | 约 8–16px | 同层一致，避免多层叠加 |
| 搜索输入 | 约 220–280px | 日期范围可更宽；不要所有控件等分 |
| 控件/面板圆角 | 约 2–6px | 服从现有库，不让后台变成胶囊集合 |

不通过极小字体压缩密度，不随视口宽度缩放字体。字号和间距改变前先减少重复标题、空区域和不必要包装。

## 色彩与表面

采用现有语义变量：页面背景、内容表面、浮层、主文字、次文字、边框、主操作、危险/警告/成功、focus。组件消费语义变量，框架变量集中映射。为主题切换打好变量基础不等于增加切换入口。

已有主色直接沿用。缺少视觉基准时使用中性表面与清晰文字层级，再确认品牌色；不要给每个模块随机配色。状态用文字/图标共同表达，不能只靠颜色。

表头、条纹、悬停和选中是不同语义：表头帮助定位列，条纹很浅，悬停局部反馈，选中明确可辨。核对四种背景下文字对比度。金额数字对齐便于比较，状态标签不过度饱和。

边框用于表格和必要分界，阴影用于有层级的浮层。页面区域可以通过细分隔和表面区分，不要嵌套卡片或所有区块加相同投影。长详情通过小标题和字段对齐分组。

## 操作位置和信息权重

- Header：全局导航与用户相关动作；页面已有标题上下文时保持一致。
- 查询区：筛选、查询、重置；业务新增通常放下方列表工具栏。
- 列表工具栏：无既定规范的新列表，推荐左侧依次放视图/状态切换、创建类主操作、批量/管理/导入等其他操作；说明与列显示等辅助工具靠右。视图切换先于其控制的状态筛选，创建类动作突出主操作，批量动作关联选中状态。已有不同约定先遵循项目，不机械重排表单选项、弹窗底部或有步骤依赖的操作。
- 行操作：优先常用动作，低频动作按现有更多菜单收纳；不可因视觉收纳改变权限或隐藏唯一入口。
- 详情：识别信息在前，当前状态及关键字段邻近，历史记录在后；动作属于正确业务对象。只读信息优先清晰文字，避免满屏禁用输入框；需要编辑时切换为对应控件，保留标签位置、原值提示、字段权限及校验规则。
- 编辑：短字段按业务关系并列，长文本全行，错误靠近字段，主保存位置稳定。

稳定尺寸避免 loading、hover、数字位数变化导致控件跳动。图标动作提供可访问名称，陌生图标提供 tooltip；沿用项目已有图标封装，不复制参考项目私有图标配置。

只读表格的普通文本采用一致的溢出处理并提供完整查看途径；Element 项目可用表格级 show-overflow-tooltip，复制、链接及复合内容列按自身交互处理。行内编辑控件不得被截断或被提示层遮挡。空值、零值和未填状态按真实业务区分，不用 truthy 判断把有效的 0 显示为空。

## 常用按钮的图标与颜色

同一操作区域突出当前任务的主动作，其他动作沿用次级或文字按钮，不把所有按钮都设成主题实心样式。主次按工具栏、行操作、弹层底部各自的任务判断，不要求整页只能有一个主按钮；危险色仅表达真实危险动作，不作为装饰强调色。

可见动作数量按使用频率、空间和上下文决定，不设全项目固定上限。常用动作直接可达，低频动作可沿用“更多”；收纳后仍要可发现，不为整齐隐藏关键入口或缩小按钮。图标辅助识别，不改变动作的主次层级。

新增或统一常用按钮图标时，优先沿用项目图标规范；使用 Iconify 时推荐 Carbon 图标集。图标选择入口：https://icon-sets.iconify.design/carbon/ 。按实际动作核对候选图标的名称与含义。

- 新增、编辑、保存、搜索、重置、刷新、删除、导入导出等常用动作，尽量采用“语义图标 + 文字”。先看当前项目同动作已有图标，保持一致；按真实行为选图标，不按外观随意挑选，也不混淆返回、撤销、重置、刷新或下载、导出。
- 沿用现有 Iconify/Carbon 封装、命名方式及图标尺寸。项目已有其他明确规范时先遵循，不为局部按钮批量替换图标库；缺少依赖时不自动安装，说明接入影响后按授权处理。实际图标标识使用前从现有代码或图标集核对，不猜名字。
- 图标默认跟随按钮文字颜色（如 currentColor），主操作、普通操作、危险操作及禁用态使用项目现有主题语义。删除等危险动作按约定表达，不给每个图标随机配色；hover、loading 和 disabled 保持一致，不硬编码另一项目的主题色。
- 同组按钮的图标大小、文字间距和对齐统一，不因加图标缩小按钮。按钮变宽时核对工具栏换行、操作列及弹层底部，不挤掉关键动作。loading 沿用组件机制，不重复叠加忙碌图标。
- 图标辅助识别，普通业务按钮保留清楚的文字；空间受限且语义明确时才沿用纯图标按钮，并提供可访问名称及必要 tooltip。无法找到准确图标时宁可保留文字，不为凑图标误导用户。

## 用具体收益判断设计是否更好

结合原问题选择一项可观察收益：同一窗口下记录区更充足、关键动作更容易找到、详情更容易扫读、重复请求减少或失败后能继续操作。保留业务字段和可达入口；用隐藏必要信息换来的“简洁”不算改善。

对照需要来自可比条件：布局用相同视口与相近内容；请求优化区分首次进入、重复打开及切换对象。只报告实际观察到的变化，不从组件拆分或请求数量推导整机性能提升，也不为普通样式任务新增性能测量。

## 诊断到修改

| 观察 | 优先修改 | 不应直接推断 |
| --- | --- | --- |
| 首屏只有少量记录 | 消除重复标题、检查筛选高度与叠加 padding | 全部改为极小字号 |
| 页面显得散 | 统一对齐基线、减少随机宽度、明确分组 | 每区块加卡片 |
| 窗口很宽却只用中间 | 放开业务容器宽度，局部约束表单 | 所有字段无限拉长 |
| 颜色很多找不到重点 | 收敛品牌/状态/链接语义 | 改掉项目品牌色 |
| 操作列挤占业务数据 | 调整常用/低频动作及实际最小宽度 | 隐藏唯一操作或权限判断 |
| 信息密但难扫读 | 优化列顺序、数字对齐、次级信息权重 | 一律增加行高 |

需要截图对比时使用真实窗口及相同或可比的数据条件；截图范围与本批改动对应，已有适用证据可复用。代码中的 token 正确不代表实际控件高度或视觉层级正确。
